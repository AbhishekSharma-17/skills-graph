# Project Structure & Configuration

> Source: https://docs.astro.build/en/basics/project-structure/ and https://docs.astro.build/en/reference/configuration-reference/

## Directory Conventions

Astro only enforces meaning on two directories: **`src/pages/`** (routes) and **`public/`** (static assets). The rest are conventions that make projects predictable across teams.

```
my-site/
├── astro.config.mjs            # Framework config
├── tsconfig.json               # Extends astro/tsconfigs/strict
├── package.json
├── public/                     # Copied as-is to dist/ root
│   ├── favicon.svg
│   ├── robots.txt
│   └── og-image.png
└── src/
    ├── pages/                  # ROUTES: .astro, .md, .mdx, .html, .ts/.js
    │   ├── index.astro         # → /
    │   ├── about.astro         # → /about
    │   ├── blog/
    │   │   ├── [slug].astro    # → /blog/:slug
    │   │   └── index.astro     # → /blog
    │   └── api/
    │       └── contact.ts      # → /api/contact (endpoint)
    ├── layouts/                # Shell components wrapping pages
    ├── components/             # .astro + framework components
    ├── content/                # Content Collections (config.ts here)
    │   └── config.ts
    ├── styles/                 # Global CSS
    ├── assets/                 # Imported assets (processed by Vite)
    ├── actions/                # Astro Actions
    │   └── index.ts
    ├── middleware.ts           # or src/middleware/index.ts
    └── env.d.ts                # /// <reference types="astro/client" />
```

### `public/` vs `src/assets/`

- `public/favicon.svg` → copied verbatim to `dist/favicon.svg`. Referenced in HTML as `/favicon.svg`. Not hashed, not optimized.
- `src/assets/hero.png` → must be imported (`import hero from "../assets/hero.png"`). Astro processes, hashes, and optimizes it. Use for every image embedded in components.

**Rule of thumb:** `public/` for anything referenced by a **fixed path** (favicon, robots.txt, `og-image.png`). `src/assets/` for anything referenced by **import**.

## `astro.config.mjs`

The root config. Astro supports `.mjs`, `.ts`, `.cjs` — prefer `.mjs` or `.ts`.

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import tailwind from "@astrojs/tailwind";
import react from "@astrojs/react";
import mdx from "@astrojs/mdx";
import node from "@astrojs/node";

export default defineConfig({
  // Public site URL — required for sitemap, RSS, canonical links
  site: "https://example.com",
  // Base path if deploying to a subdirectory
  base: "/",
  // Trailing slash policy: "always" | "never" | "ignore"
  trailingSlash: "never",
  // Default output: "static" | "server"
  output: "static",
  // Adapter for SSR deployment
  adapter: node({ mode: "standalone" }),
  // Integrations (processed in order)
  integrations: [tailwind(), react(), mdx()],
  // Image service
  image: {
    service: { entrypoint: "astro/assets/services/sharp" },
    domains: ["images.unsplash.com"],
  },
  // i18n
  i18n: {
    defaultLocale: "en",
    locales: ["en", "fr", "de"],
    routing: { prefixDefaultLocale: false },
  },
  // Vite escape hatch
  vite: {
    ssr: { noExternal: ["some-esm-only-pkg"] },
  },
  // Experimental flags
  experimental: {
    svg: true,
  },
});
```

### The Config Keys You Will Actually Use

| Key | Purpose |
|-----|---------|
| `site` | Your production URL. Many integrations (sitemap, RSS) require this. |
| `output` | `"static"` (default) or `"server"`. Drives adapter requirements. |
| `adapter` | Required when `output: "server"` and for any deployment target. |
| `integrations` | `[]` of integration plugins — installed via `astro add` or manually. |
| `redirects` | Static redirects map: `{ "/old": "/new" }` or `{ "/old": { status: 302, destination: "/new" } }`. |
| `server.port` | Change the dev server port (default 4321). |
| `build.format` | `"directory"` (default, `/about/index.html`) or `"file"` (`/about.html`). |
| `build.assets` | Output directory for processed assets (default `"_astro"`). |
| `vite` | Full Vite config passthrough — use sparingly. |

## TypeScript Setup

Astro ships with three base configs. Extend one in `tsconfig.json`:

```jsonc
{
  "extends": "astro/tsconfigs/strict",
  "include": [".astro/types.d.ts", "**/*"],
  "exclude": ["dist"],
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "~/*": ["src/*"]
    }
  }
}
```

| Preset | When to use |
|--------|-------------|
| `astro/tsconfigs/base` | Loose — JS projects or quick prototypes |
| `astro/tsconfigs/strict` | **Recommended default** — strict mode on |
| `astro/tsconfigs/strictest` | Very pedantic — for greenfield TS projects |

### Auto-Generated Types

`.astro/types.d.ts` is generated by `astro sync` / `astro dev` and includes:

- Route param types (`"/blog/[slug]"` → `{ slug: string }`).
- `astro:content` type definitions for your collections.
- `astro:env` type definitions.
- `astro:assets` image module declarations.

Run `astro sync` manually after editing `src/content/config.ts` or env schema if HMR doesn't pick up the change.

## Path Aliases

Use `tsconfig.json` `paths` — Astro's Vite pipeline respects them.

```jsonc
{
  "compilerOptions": {
    "paths": {
      "~/*": ["src/*"],
      "@components/*": ["src/components/*"]
    }
  }
}
```

Then in any `.astro` / `.ts`:

```astro
---
import Hero from "~/components/Hero.astro";
import { posts } from "@components/data/posts";
---
```

## Environment Variables

Astro exposes two mechanisms:

1. **`import.meta.env`** — Vite-native. Exposed at build time. Only keys starting with `PUBLIC_` are shipped to the browser.

```bash
# .env
PUBLIC_API_URL=https://api.example.com   # Available client-side
DATABASE_URL=postgres://...              # Server-only
```

```astro
---
const apiUrl = import.meta.env.PUBLIC_API_URL;     // OK on client or server
const db = import.meta.env.DATABASE_URL;           // Only available server-side
---
```

2. **`astro:env`** (recommended in v5+) — type-safe schema with runtime validation.

```ts
// astro.config.mjs
import { defineConfig, envField } from "astro/config";

export default defineConfig({
  env: {
    schema: {
      PUBLIC_API_URL: envField.string({ context: "client", access: "public" }),
      DATABASE_URL: envField.string({ context: "server", access: "secret" }),
      PORT: envField.number({ context: "server", access: "public", default: 4321 }),
      STRIPE_ENABLED: envField.boolean({ context: "server", access: "public", default: false }),
    },
  },
});
```

```ts
// src/server/db.ts
import { DATABASE_URL } from "astro:env/server";
// ↑ typed + throws at startup if missing
```

```astro
---
import { PUBLIC_API_URL } from "astro:env/client";
---
<a href={PUBLIC_API_URL}>API</a>
```

## .env File Loading

| File | Loaded when |
|------|-------------|
| `.env` | Always |
| `.env.local` | Always, gitignored by default |
| `.env.development`, `.env.production` | Based on `import.meta.env.MODE` |
| `.env.development.local`, `.env.production.local` | Mode-specific + gitignored |

**Never commit `.env.local` or any secrets.** Astro's starter `.gitignore` handles this, but verify on existing repos.

## Common Pitfalls

- **Not setting `site`** → sitemap and RSS integrations produce invalid URLs.
- **Using `public/` for component images** → you lose hashing, optimization, and responsive srcsets. Import from `src/` instead.
- **Mixing `trailingSlash` policies across environments** → your CDN rewrites and Astro config must agree, or you get redirect loops.
- **Editing `.astro/types.d.ts` directly** → it's regenerated. Put custom types in `src/env.d.ts` or dedicated `.d.ts` files.
- **Importing server-only code into `.astro` components that are also used client-side** (e.g., inside framework components hydrated with `client:*`) → the server-only code leaks into the client bundle. Gate with `import.meta.env.SSR` or keep server utilities in endpoints/actions.
